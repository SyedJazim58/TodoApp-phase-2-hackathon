# Data Model: Task Entity

**Feature**: 001-backend-core-data
**Date**: 2026-02-07
**Purpose**: Define Task entity schema, validation rules, and relationships

## Entity Overview

**Task**: Represents a user's todo item with completion tracking. Core entity for multi-user task management system with strict ownership enforcement.

**Ownership Model**: Single-owner - one task belongs to exactly one user. User_id is non-nullable and immutable after creation.

## SQLModel Definition

**File**: `backend/src/models/task.py`

```python
from sqlmodel import SQLModel, Field
from datetime import datetime
from typing import Optional

class Task(SQLModel, table=True):
    """
    Task model with strict user ownership.

    Security: All queries MUST filter by user_id to enforce data isolation.
    """
    __tablename__ = "tasks"

    # Primary key - auto-increment integer
    id: Optional[int] = Field(default=None, primary_key=True)

    # Ownership - non-nullable foreign key to user (user table managed by auth layer)
    user_id: str = Field(nullable=False, index=True)

    # Task data
    title: str = Field(max_length=200, nullable=False)
    description: Optional[str] = Field(default=None, max_length=2000)
    completed: bool = Field(default=False, nullable=False)

    # Timestamps - UTC timezone
    created_at: datetime = Field(default_factory=datetime.utcnow, nullable=False)
    updated_at: datetime = Field(default_factory=datetime.utcnow, nullable=False)
```

## Field Specifications

### id (Primary Key)

- **Type**: Integer (auto-increment)
- **Nullable**: No (after creation)
- **Default**: None (auto-generated by database)
- **Constraints**: PRIMARY KEY, UNIQUE
- **Purpose**: Unique identifier for each task
- **Security Note**: Sequential integers acceptable; ownership verification prevents unauthorized access

### user_id (Ownership)

- **Type**: String (VARCHAR 255)
- **Nullable**: No (required at creation)
- **Default**: None (must be provided)
- **Constraints**: NOT NULL, INDEXED
- **Purpose**: Identifies owning user (opaque reference to auth layer)
- **Immutability**: Cannot be changed after task creation
- **Index**: Yes (for efficient user-scoped queries)

### title (Task Content)

- **Type**: String (VARCHAR 200)
- **Nullable**: No (required)
- **Default**: None
- **Constraints**: NOT NULL, MAX_LENGTH 200
- **Purpose**: Brief description of task
- **Validation**: Pydantic enforces max length before database interaction

### description (Optional Details)

- **Type**: String (VARCHAR 2000)
- **Nullable**: Yes (optional)
- **Default**: None
- **Constraints**: MAX_LENGTH 2000
- **Purpose**: Extended task details or notes
- **Validation**: Pydantic enforces max length if provided

### completed (Status)

- **Type**: Boolean
- **Nullable**: No
- **Default**: False
- **Constraints**: NOT NULL
- **Purpose**: Tracks task completion status
- **State Transitions**: False ⇔ True (toggleable)

### created_at (Audit)

- **Type**: Timestamp (datetime)
- **Nullable**: No
- **Default**: datetime.utcnow() at creation
- **Constraints**: NOT NULL
- **Purpose**: Record creation time
- **Immutability**: Set once at creation, never modified
- **Timezone**: UTC

### updated_at (Audit)

- **Type**: Timestamp (datetime)
- **Nullable**: No
- **Default**: datetime.utcnow() at creation
- **Constraints**: NOT NULL
- **Purpose**: Record last modification time
- **Mutability**: Refreshed on every update operation
- **Timezone**: UTC

## Database Schema

### Table: tasks

| Column       | Type         | Constraints                    | Index | Notes                       |
|--------------|--------------|--------------------------------|-------|-----------------------------|
| id           | INTEGER      | PRIMARY KEY, AUTO_INCREMENT    | PK    | Sequential integer          |
| user_id      | VARCHAR(255) | NOT NULL                       | Yes   | Efficient user-scoped queries |
| title        | VARCHAR(200) | NOT NULL                       | No    | Required task description   |
| description  | VARCHAR(2000)| NULL                           | No    | Optional extended details   |
| completed    | BOOLEAN      | NOT NULL, DEFAULT FALSE        | No    | Completion status           |
| created_at   | TIMESTAMP    | NOT NULL                       | No    | UTC timestamp               |
| updated_at   | TIMESTAMP    | NOT NULL                       | No    | UTC timestamp               |

### Indexes

1. **PRIMARY KEY (id)**: Automatic with primary key declaration
2. **INDEX (user_id)**: Declared in SQLModel Field with `index=True`

**Rationale for user_id index**: All queries filter by user_id, making this index critical for performance. Without index, queries would scan entire table.

### Foreign Keys

**None**: user_id is an opaque reference. Auth layer manages users; this data layer does not enforce foreign key constraints to user table (which may not exist in same database).

## Validation Rules

### Pydantic Validation (Application Layer)

1. **user_id**:
   - Must be non-empty string
   - Validated by Pydantic on model instantiation
   - Cannot be changed after creation (enforced by service layer)

2. **title**:
   - Must be non-empty string
   - Maximum 200 characters
   - Validated before database write

3. **description**:
   - Optional (None allowed)
   - Maximum 2000 characters if provided
   - Validated before database write

4. **completed**:
   - Must be boolean (True/False)
   - Defaults to False if not specified

5. **Timestamps**:
   - Managed by application (not user input)
   - Always UTC timezone
   - created_at: Set once at creation
   - updated_at: Refreshed on modification

### Database Constraints

1. **NOT NULL constraints**: Enforced on user_id, title, completed, created_at, updated_at
2. **DEFAULT constraints**: completed defaults to FALSE
3. **Type constraints**: Integer for id, varchar for strings, boolean for completed, timestamp for dates

## Relationships

**None** - Task is standalone entity.

**Why no relationships?**:
- user_id is opaque reference to external auth system
- No task-to-task relationships in MVP scope
- Future features may add relationships (e.g., subtasks, categories)

## State Transitions

### Completion Status

```
┌─────────────┐          toggle          ┌─────────────┐
│ completed = │ ────────────────────────> │ completed = │
│    False    │                           │    True     │
│ (Incomplete)│ <──────────────────────── │ (Complete)  │
└─────────────┘          toggle          └─────────────┘
```

**Rules**:
- Only one allowed transition: toggle between True/False
- No intermediate states
- updated_at timestamp refreshed on every toggle

### Lifecycle

```
[Create] ──> [Update*] ──> [Delete]
             └──> [Toggle Complete*]
```

**States**:
1. **Non-existent**: Task not in database
2. **Created**: Task exists with completed=False (default)
3. **Updated**: Task modified (title, description, or completed changed)
4. **Deleted**: Task removed from database (not soft-deleted)

**Notes**:
- Updates can happen multiple times
- Toggle is special case of update (flips completed boolean)
- No soft delete or archival in MVP scope
- All state transitions verify ownership

## Security Constraints

### Ownership Enforcement

**Rule**: Every database operation MUST filter by user_id

**Implementation**:
```python
# Good: Query includes user_id filter
statement = select(Task).where(
    Task.id == task_id,
    Task.user_id == user_id
)

# Bad: Query without user_id filter (NEVER DO THIS)
statement = select(Task).where(Task.id == task_id)
```

### Immutable Fields

- **user_id**: Cannot be changed after creation
- **id**: Auto-generated, not user-controlled
- **created_at**: Set once at creation

### Mutable Fields

- **title**: Can be updated
- **description**: Can be updated
- **completed**: Can be toggled
- **updated_at**: Automatically refreshed on modification

## Example Usage

### Create Task

```python
from models.task import Task
from datetime import datetime

task = Task(
    user_id="user123",
    title="Buy groceries",
    description="Milk, bread, eggs",
    completed=False
)
# created_at and updated_at set automatically
# id generated by database
```

### Query User's Tasks

```python
from sqlmodel import Session, select

with Session(engine) as session:
    statement = select(Task).where(Task.user_id == "user123")
    tasks = session.exec(statement).all()
```

### Update Task

```python
# Fetch with ownership verification
task = session.exec(select(Task).where(
    Task.id == 42,
    Task.user_id == "user123"
)).first()

if task:
    task.title = "Buy groceries and cook dinner"
    task.updated_at = datetime.utcnow()  # Refresh timestamp
    session.add(task)
    session.commit()
```

### Toggle Completion

```python
task = session.exec(select(Task).where(
    Task.id == 42,
    Task.user_id == "user123"
)).first()

if task:
    task.completed = not task.completed
    task.updated_at = datetime.utcnow()
    session.add(task)
    session.commit()
```

## Testing Considerations

### Unit Tests (Model Validation)

1. Task creation with all fields
2. Task creation with minimal fields (title only)
3. Validation failures (title too long, invalid types)
4. Default values (completed=False, timestamps auto-set)

### Integration Tests (Database Operations)

1. Create task and verify persistence
2. Query by user_id filters correctly
3. Update refreshes updated_at
4. Ownership verification (User A cannot access User B's task)
5. Concurrent modifications (last-write-wins behavior)

### Critical Test Cases

1. **Cross-user isolation**: User A's query excludes User B's tasks
2. **Ownership verification**: Accessing task with wrong user_id returns no result
3. **Timestamp management**: created_at immutable, updated_at refreshed
4. **Validation**: Max length constraints enforced
5. **State consistency**: No orphaned tasks (all tasks have user_id)
